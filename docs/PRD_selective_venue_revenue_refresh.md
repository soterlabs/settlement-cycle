# PRD: refresh API revenue for selected venues

Status: proposed follow-up PR. This document does not enable or publish API updates.

## Problem and outcome

A correction to one allocation currently requires recalculating a whole prime's
API result, including unrelated multichain events and balances. Operators need
to refresh explicitly selected venues while preserving every other venue's
calculation and retaining honest provenance for the combined result.

The first use case is September 2026: Spark S1 reserve-treasury revenue and
Grove E10 BUIDL valuation/redemption cash realization. PR #223 refreshes their
settlement artifacts separately. Those refreshed settlement results must not
be described as matching the older API revisions until the API is updated.

## Scope and interface

Provide a CLI accepting a prime, an explicit list of venue IDs, a date range,
and an output directory. Default to a dry run; require an explicit publish
flag to change the API's latest revisions. Reject unknown/duplicate venues,
missing baselines, unsupported dependencies, and ambiguous date ranges.
Example interface (proposed, not currently executable):

```
settle revenue refresh-venues --prime spark --venues S1 \
  --from 2026-09-01 --through 2026-09-30 --output preview/spark
settle revenue refresh-venues --prime grove --venues E10 \
  --from 2026-09-01 --through 2026-09-30 --output preview/grove
```

The command prints the planned inputs to fetch, saved inputs to reuse, dependent
fields to recompute, and affected API cutoffs. It never expands into a full-prime
replay silently. No settlement publication, DR replay, historical true-up,
borrowed-capital tracing, or prior-month report regeneration is in scope.

## Calculation and dependency plan

API daily records contain month-to-date results. Recalculate each affected
cutoff independently from its pinned baseline, not by repeatedly adding a delta
to the preceding newly published result. A correction effective September 6
requires all September cutoffs from September 6 onward. Changes to an opening
balance can affect the entire month; cross-month corrections require an explicit
expanded plan. Include the first minute of the month consistently with the
existing period convention. Honor each venue's effective dates.

Reuse the shared production daily/monthly venue computation. Fetch only inputs
required for selected venues and their explicit dependencies. A reward-only
change can reuse native yield, balances and principal flows; a rate-only change
can reuse daily debt and deductions without multichain reads. Missing or failed
provider data must not become zero revenue. Support resumable input collection
through the existing cache and indexer checkpoints.

Recompose the complete prime result in memory. Preserve unselected venues'
revenue and source records exactly. Recalculate affected totals, SDE revenue,
borrowing costs, reimbursement, PnL and report-only CoF allocations using saved
daily debt, rates, idle balances and other deductions. It is legitimate for a
shared total or CoF allocation to change; show it separately from native venue
revenue. Never copy a stale aggregate after replacing a venue row.

For E10, reuse unchanged balances while applying the dated NAV haircut, restore
verified small redemption exits to principal flows, and recognize only cash
minus the request's dated carrying value. Carry outstanding requests across
cutoffs and months without a T+1/T+3 lookback limit. Cash and share legs must
not both book the same economic revenue. The September boundary fee belongs
in E10 once; do not increase the historical Sky adjustment a second time.

For S1, newly allowlisted treasury receipts increase external revenue only.
They must not cause the existing native aToken yield or previously booked
external rewards to be added twice. Selecting S1 does not authorize refreshing
S2-S5, even if their configuration changed in the same upstream PR.

## Baselines and provenance

Capture immutable source revision IDs, hashes, closing/opening pins, schema
version, configuration/input hashes, rate snapshot and per-venue lineage before
work begins. Record the new code/configuration version for recalculated inputs
and the original versions for reused fields. A partially refreshed result must
not claim that all inputs were generated by the new code.

Define and test explicit compatible-schema migrations for reusable snapshots.
Do not weaken the existing strict decoder or code/config compatibility guards.
Refuse incompatible baselines with an actionable explanation. A plan must
verify that configuration changes outside the selection have not been silently
applied to reused data. Explicitly label deliberate retention of old values.

Persist an audit manifest with before/after venue and aggregate amounts,
selected source events, input coverage, network calls by venue/chain, and
unchanged-field comparisons. Include a deterministic calculation identity so
retries cannot add the same correction twice. Keep all amounts as Decimals.

## Publication, concurrency and recovery

Stage complete immutable revisions for every cutoff and validate them before
making them visible. Use a prime-scoped lock and compare-and-swap against every
captured latest revision so the ordinary daily worker cannot overwrite or be
overwritten by a stale refresh. Prefer one atomic promotion of the selected
range; if the storage design requires batches, expose explicit batch status and
never describe a partly refreshed range as complete.

Checkpoint collection, calculation, validation and publication separately.
Restart from verified checkpoints, not a partially mutated result. A retry
with the same identity is a no-op for already published revisions. Preserve
old revisions for audited rollback; do not delete or rewrite historical rows.
The public API shape should remain compatible, with refresh lineage available
through provenance/status rather than implementation details in chart labels.

## Validation and acceptance

- Only selected venue inputs are fetched; unrelated venues/chains and DR are
  never replayed. Tests fail on unexpected extraction calls.
- Every affected MTD cutoff is corrected. Unselected primes, dates and native
  venue revenues remain unchanged, byte-for-byte where schema permits.
- S1 reward-only refresh leaves native yield and borrowing costs unchanged.
- E10 fixed-SDE realization changes Sky revenue exactly once; haircut-driven
  CoF changes reconcile with saved daily debt/rates and changed SDE values.
- Aggregates reconcile to components, with an explicitly documented tolerance
  only for Decimal context noise. No new publication APY warning is required.
- September 30 updated API results agree with the corresponding refreshed
  settlement supply-side inputs, excluding separately imported DR and payment
  adjustments. For unsupported comparisons, report the limitation explicitly.
- Test month boundaries, missing baselines, incompatible schema, effective-date
  cuts, duplicate receipts, outstanding redemptions, failed RPC/indexer calls,
  interrupted runs, idempotent retries and concurrent daily publication.
- A dry run performs no API writes. Publication preserves old revisions and
  produces an audit that proves the promised selection and dependency scope.

Roll out with the two September examples, inspect the preview, publish the
requested range, then read back all selected API records and compare hashes.
Keep January-August published settlements untouched.
